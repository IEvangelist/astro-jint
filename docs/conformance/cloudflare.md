A loop-generated `it` counts once, whatever the number of cases it makes: `routing-priority` (22 routes per test), `default-image-service` (three static instances), `compile-image-service`, `binding-build-image-service`, `integration-defined-image-service`, `image-config` and the build/sync loop of `typegen-phase`. The suite skips the 19 gap tests, and nothing else.

Every ported test asserts something that is true of the official adapter; the "adapted" ones keep its intent and change the scenario, the place where the answer is read, or the exact expectation, and say so in the XML doc of their class.

## Differences

- **HTTP against the host, not workerd or the dev server.** Upstream starts the Astro dev server (workerd through the Cloudflare Vite plugin), `astro preview` (wrangler), or builds and reads `dist/` and the generated `wrangler.json`, and it unit-tests modules of the adapter. Every ported test builds a fixture with the harness and sends HTTP requests to the ASP.NET host, which runs the server bundle in Jint. Dev-server tests whose assertions are about what a site serves (`routing-priority`, the middleware test of `sessions`, `prerender-node-env`) are adapted to requests to the built site; those about the dev server itself (optimizer, HMR, dependency scan, allowed hosts, the dev image endpoint) are N/A, or become an assertion on the build log (`BuildLog`) when the message belongs to the build (`top-level-return`, `ssr-deps`, `ts-astro-import`, `with-react`).
- **Build output.** `client/` (the files that are served), `server/entry.mjs` with `server/chunks/*.mjs` (the server build is code-split) and `astro-jint.json`; no `_worker.js`, `wrangler.json`, `_headers`, `_redirects` or `.assetsignore`. Tests that snapshot those files ask what they cause: redirects answer 301 with `Location`, hashed assets are served with `Cache-Control: public, max-age=31536000, immutable` (`HeadersTests`, `WithBaseTests`), the base is removed from the URL by the host, so the files are not under a `blog` folder as upstream's are. `build.serverEntry` is honoured (`ServerEntryTests`).
- **Platform headers.** The host never believes `cf-connecting-ip` unless ASP.NET Core's forwarded-headers middleware is told to. `ClientAddressTests` and `CfHelpersTests` set it up as a site behind Cloudflare would (`CfPages.BehindCloudflareAsync`), and an extra test proves that the header is ignored otherwise. Where the helper of the adapter returns `undefined` the host has the address of the connection, and where upstream answers 500 to a header with a payload the middleware ignores a value that is not an IP address and the host answers 200 without the payload in the response. `request.cf`, `Cloudflare-CDN-Cache-Control` and the Worker version are N/A.
- **Environment.** `astro:env` public variables are read at build time, from `.env.production`; secrets are given to the host through `AstroOptions.Env` at run time. Upstream uses wrangler `vars`, `.dev.vars` and `env` of `cloudflare:workers`.
- **Sessions.** The session driver is backed by the `IDistributedCache` of the host (fixture `sessions`, shared with the Node tests); the Cloudflare KV namespace and its binding tests are N/A.
- **Image service.** The adapter replaces Sharp with the pass-through service, for the build as well as at run time, because Jint cannot run it. What upstream converts with Sharp (build) or the Images binding (run time) is a gap (GAP-CF-5, GAP-CF-6, GAP-CF-7); the tests that check URLs, SVG pass-through, domain refusals and statuses pass. A request without `href` is answered with 400 by the handler of Astro, where the Images binding endpoint says 403, and the host does not follow a redirect of a remote picture and answers 500 where upstream says 404. The adapter has no `imageService` or `prerenderEnvironment` option, so the loops of upstream have one instance.
- **Prerender.** The build prerenders with Astro's default in-process prerenderer, so the workerd prerenderer (framing, queues, Durable Objects, `nodejs_als` attribution, its error messages and its incremental protocol) is N/A. `ProductionAsyncHooksTests` builds a site with `experimental.incrementalBuild` as a smoke test.
- **Chunked collection storage.** The Cloudflare adapter turns `collectionStorage: 'chunked'` into chunks of 1 MiB (workerd limits the size of a module); Astro's default is 20 MiB, so `ContentCollectionsChunkedTests` asks for `{ type: 'chunked', chunkSize: 1048576 }` itself. The build writes the manifest of the data store to the cache directory.
- **Static file index.** The host indexes `client/` when it starts, so a file that is written to it afterwards is not served; the "falls back to the assets binding" test of `custom-entryfile-fetch-state` writes the file between the build and the start of a host of its own, as upstream does between the build and the preview.
- **Fixtures.** The 56 upstream fixtures are consolidated into 7: `cf-pages` (hybrid site: prerendered and on-demand pages, endpoints, server islands, images, redirects, cookies, the cache provider routes; variants cover `base`, `build.assets`, `output: 'static'`, the cache probe and the image services), `cf-routing`, `cf-env`, `cf-sql` (its own fixture, as its build fails), `cf-ui` (React, Solid, Svelte and Vue in one build), `cf-content` (Code and Prism pages, content collection, actions, server entry, dependency-scan pages) and `cf-chunked`, plus the existing `sessions`. The integration `cf-image-service` is appended to `support/integrations.mjs` (it registers an image service from `astro:config:setup`), and so is `cf-shiki-js-engine` (a Vite plugin that answers the import `#shiki-engine`, for the extra test of `AstroDevPlatformTests`). The pages `prism-prerendered.astro` and `code-prerendered.astro` of `cf-content` have `prerender = true`: the first guards the build with the Prism component, which the adapter has to make possible, and the second shows that the Code component works in a prerendered page.

## Gaps

GAP-CF-8, GAP-CF-9 and GAP-CF-10 are fixed and kept here for the record. Each open gap is reproduced by removing the `Skip` of the test named and running its class: `dotnet test --project tests/AstroJint.Conformance.Tests/AstroJint.Conformance.Tests.csproj -- --filter-class AstroJint.Conformance.Cloudflare.<Class>` (the first lines of the output of the host are in `CfContent.Describe` and in `ConformanceSite.Logs`).

- **GAP-CF-1**: a page that imports a `.sql` file (`import query from '../query.sql'`) fails the build: `[vite] Build failed`, `[PARSE_ERROR] Expected a semicolon or an implicit semicolon after a statement, but found none (src/query.sql:1:14)`. Vite parses an unknown extension as JavaScript; Cloudflare's runtime has `.sql` (and `.wasm`) as native module types. Skipped test: "SQL Import: build: can import .sql files" in `SqlImportTests` (fixture `cf-sql`). Suspected area: the Vite config of `packages/astro-adapter-jint` (no plain-text handling for `.sql`). Reproduce: `pnpm exec astro build` in `tests/conformance/fixtures/cf-sql` prints the error and exits with code 1 (the page `/` is never reached); or remove the `Skip` of the test and run `dotnet test --project tests/AstroJint.Conformance.Tests/AstroJint.Conformance.Tests.csproj -- --filter-class AstroJint.Conformance.Cloudflare.SqlImportTests`.
- **GAP-CF-2**: an endpoint that sets a cookie and returns `Response.redirect()` answers an empty 500 where 302, `Location` and `Set-Cookie` are expected: `TypeError: Failed to execute 'append' on 'Headers': Headers are immutable`. In Astro 7.3.8 `core/app/prepare-response.js` appends `Set-Cookie` to the headers of the response when `render()` is called with `addCookieHeader: true`, and the headers of `Response.redirect()` are immutable. Skipped tests: "preserves cookies when finalizing immutable Hono responses" in `CustomEntryfileFetchStateTests` and "rebuilds a response with immutable headers" in `ResponseTests`. Suspected area: `packages/astro-adapter-jint/src/server.ts`, which calls `app.render(request, { addCookieHeader: true })`; the Cloudflare entry finalizes through `astro/fetch`. Reproduce: `GET /immutable-redirect` on `cf-pages`.
- **GAP-CF-3**: the cookies set before a page throws are dropped from the custom 500 page: `GET /error` on `cf-pages` (the page sets `before-error=1` and throws) answers 500 with the body of the custom error page and no `Set-Cookie`. Astro's `app.render()` renders the error page from the state of the failed request without its cookies; the Cloudflare entry keeps them through the composable `astro/fetch` API (`FetchState` and `finalize()`). Skipped test: "preserves cookies when rendering a custom error page" in `CustomEntryfileFetchStateTests`. Suspected area: `packages/astro-adapter-jint/src/server.ts` (`app.render()` instead of `astro/fetch`).
- **GAP-CF-4**: a cache provider's `onRequest` gets no `waitUntil`: the probe provider of `cf-pages` reads `typeof context.waitUntil` as `undefined` (header `x-cache-provider-waituntil: undefined`, `function` expected) because the host renders with `app.render()` and passes none. Skipped test: "passes Cloudflare waitUntil through to CacheProvider.onRequest" in `CacheProviderWaitUntilTests`. Suspected area: `packages/astro-adapter-jint/src/server.ts` (render options) and the host (no hook for work after the response). Reproduce: `GET /cache/page` with the config `cache.provider.config.waitUntilProbe = true` (`CfPages.WaitUntilProbe`).
- **GAP-CF-5**: the build copies pictures instead of converting them. The adapter replaces `astro/assets/services/sharp` with the pass-through service (`index.ts`: when `image.service.entrypoint` is Sharp it uses `passthroughImageService()`) for the build as well as at run time, although Sharp itself loads fine in the Node build. Images that ask for WebP or AVIF (`<Image>` default, `<Picture formats={['avif']}>`, `getImage({ format: 'avif' })`) come out as `.jpg` copies (for example `/_astro/penguin.gLBdjEDe_Z1Hs4QF.jpg`, a byte-identical copy of the 38690-byte source; no `RIFF`/`WEBP` header). Skipped tests: in `DefaultImageServiceTests` "honors the format each component asked for" and the theory "transforms images on prerendered routes into build assets"; in `CompileImageServiceTests` "with no user image.service: generates real WEBP assets at build time" and "generates real WEBP assets at build time with prerenderEnvironment: node". Suspected area: `packages/astro-adapter-jint/src/index.ts` (keep Sharp for the build and swap only the service of the server bundle).
